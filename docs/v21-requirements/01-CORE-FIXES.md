# 01 — Core Fixes

## R-001 AI 座位预设不得锁死真人座位

### 问题

当前大厅中，房主保存 AI 座位设置后，空座位可能立即被创建为 AI Player。之后真人再加入同一座位时，会被服务端判定“座位不可用”。

### 目标

AI 座位设置必须被视为“预设”，而不是立即占有该座位的正式玩家实体。

### 推荐实现

引入独立的 `seat_presets` 或等价结构：

```json
{
  "seat": 2,
  "mode": "ai",
  "provider": "openai",
  "personality": "aggressive"
}
```

大厅阶段：

- AI 预设只保存配置，不创建正式 Player。
- 真人加入目标座位时，应优先获得该座位。
- 开始游戏时，服务端再根据仍为空的 AI 预设座位创建 AI Player。

### 兼容方案

如果短期内不新增 `seat_presets`：

- 允许真人在游戏未开始前覆盖 `owner_id == null` 的 AI 占位玩家。
- 覆盖后不得残留旧 AI session、memory、provider 配置。

### 验收

- 房主先保存 2~6 号 AI 配置，再邀请真人加入 2 号，真人可以成功加入。
- 真人离开后，若该座位仍有 AI 预设，开局时可自动补回 AI。
- 已开局后禁止真人覆盖 AI / 其他真人座位。

## R-003 死亡狼人不得继续获得新的狼队私有信息

### 问题

死亡狼人当前可能仍能通过 `owner_view()` / WebSocket 继续看到后续夜晚的狼队频道内容。

### 目标

死亡玩家不得继续获得其死亡之后生成的、仅存活阵营成员可见的私有信息。

### 规则

- 死亡狼人不得发送新的狼队消息。
- 死亡狼人不得接收死亡之后产生的狼队消息、狼队投票或战术信息。
- 是否保留死亡前已经见过的历史狼队消息，可由产品规则决定；默认允许保留历史，不允许新增。
- InformationScope 必须在服务端做过滤，不能依赖前端隐藏。

### 验收

1. 狼人 A、B 存活时，双方可见狼队讨论。
2. A 死亡后，B 在下一晚发出的新消息不得出现在 A 的 snapshot、增量事件或重连恢复数据中。
3. A 刷新、断线重连后仍不得获得死亡后的狼队信息。

## R-007 Provider / fallback 状态必须可见

### 问题

用户可以选择 OpenAI / Anthropic / Gemini，但服务器未配置密钥或模型调用失败时会 fallback 到 Mock。当前前端没有清晰展示真实执行状态。

### 要求

客户端应展示每个 Provider 至少以下状态：

- 可用
- 未配置
- 临时不可用
- 已 fallback 到 Mock

大厅选择模型时：

- 未配置 Provider 推荐直接禁用。
- 如果允许选择，必须明确标注“将使用 Mock 回退”。

游戏过程中：

- 管理员 / 房主可查看当前 AI 实际 Provider。
- 若某次请求 fallback，应记录 provider、错误分类、fallback 原因。
- 普通玩家无需看到 API Key、错误堆栈等敏感信息。

### 验收

- 未设置 OpenAI Key 时，UI 不得表现为“正在使用 OpenAI”却实际使用 Mock。
- 模型调用失败并回退时，后台日志可追踪。
